## Source obligations and implementation sequence

1. **Registration:** `scripts/register-webhook.ts <merchantSlug>` resolves one real merchant and registers `${APP_BASE_URL}/webhooks/paypal/<slug>`. Subscribe to exactly `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.CAPTURE.REVERSED`, `CUSTOMER.DISPUTE.CREATED`, `CUSTOMER.DISPUTE.UPDATED`, `CUSTOMER.DISPUTE.RESOLVED`. Save the actual returned ID in `merchants.paypal_webhook_id`. Refuse simulated merchants, missing credentials, insecure/local endpoint URLs and an existing registration. An uncertain vendor result or failure to save its returned ID requires Dashboard reconciliation before another registration attempt; no automatic mutation replay.
2. **Ingress and durability:** implement endpoint 37 at `/webhooks/paypal/:merchantSlug`, outside the `/api` prefix. Isolate the raw-body content parser to that plugin. Resolve the merchant/webhook ID and use the existing `packages/paypal` verification binding. After approval, map the explicit event allowlist and atomically persist the event plus the existing `paypal.event` job. Verify duplicates before acknowledging them. Preserve source storage of unverified rows without allowing ID poisoning.
3. **Capture reconciliation:** the worker reads an unprocessed verified event. Known orders reconcile against authoritative order details and the approved capture store. Unknown toolkit orders use `orders.get`, match merchant-owned products by SKU first and by exact name only when SKU is absent, and snapshot their current listing version. Reject ambiguous/missing products, cross-merchant IDs, mixed currency, unsupported purchase-unit/capture counts and contradictory totals rather than guessing. Create order/items and apply capture atomically or prove idempotent recovery; no capture POST is made by a webhook.
4. **Refund notifications:** reconcile the merchant-owned capture and actual authoritative payment state; do not turn a partial refund into a fully refunded order or regress a later state on an old capture event. Do not issue a refund. Reversal/approval subscriptions have no extra state transition specified by H3; document their treatment rather than inventing one.
5. **Dispute dispatch and polling:** forward `resource.dispute_id`, falling back to `resource.id`, to the H4 synchronizer. Poll each real configured merchant every minute with `updateTimeAfter`, all pages, unchanged filters and loop/size bounds. Advance a cursor only after every item/page has successfully synchronized, with overlap for boundary updates. Missing H4 implementation must be visible as pending, never a successful no-op. Preserve Ishaan's handler ownership.
6. **Composition and closeout:** wire API and worker, test normal startup/shutdown and publish focused commits with evidence. Add executable read-only local/real acceptance checks and precise human setup steps. Keep H3 formally pending until the real signed capture event and A5 pass.

Each numbered area may need more than one focused commit. No application scaffold, new provider, product UI, schema expansion or H4 approval workflow is part of this task.
